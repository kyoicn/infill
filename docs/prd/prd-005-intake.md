# PRD-005：产品录入

> 本 PRD 与 [PRD-000 产品目录](prd-000-catalog.md) 是**上下游关系**：产品录入（intake）**生产** `data/catalog.yaml` 的新内容，prd-000 **消费**它（只读展示 + 重新加载）。本 PRD 不替换 `catalog.yaml` 作为单一数据源的地位 — 写入完成后必须经过 prd-000 CUJ-2 的 `load_catalog(db)` 链路才会进入运行时 DB。

## 功能概述

`data/catalog.yaml` 是作坊主手维护的产品 / 组件 / 打印盘单一数据源。手填 YAML 的痛点：① 字段多（组件名、件数、盘号、耗时、BOM、颜色），且必须与拓竹切片软件的截图逐项对齐；② 中文键易抄错；③ 同一产品多种配色时需要重复列出整套 BOM；④ 一字之差就让 `load_catalog` 报错或在运行时撞名。

本 PRD 把这条工作流搬到网页：用户上传拓竹切片软件导出的截图（**组装图** + **打印盘截图**），由 LLM 识别 BOM 件数、每盘件数、组件名、耗时，落到草稿预览页让用户校对，再手动填入颜色（含多配色变体），最后一键 append 写入 `data/catalog.yaml` 并自动触发 prd-000 CUJ-2 的「重新加载目录」。整条链路是日常常用入口（新产品开发 / 批量补建产品时进入），不是一次性迁移工具。

本 PRD 范围：
- CUJ-1：上传截图 + 启发式自动分类为组装图 / 打印盘两栏
- CUJ-2：触发 LLM 识别（DeepSeek provider）
- CUJ-3：草稿校对 BOM + 打印盘（件数 / 耗时 / 撞名兜底）
- CUJ-4：颜色矩阵填写 + 多配色变体（每个变体独立产品条目）
- CUJ-5：合并到 `data/catalog.yaml`（备份 + 写入 + 自动 reload + 失败回滚）

不在本 PRD 范围：识别历史、置信度分数、自动 fallback 多 provider、一次上传多产品、LLM 自动推断颜色、LLM 提供商前端切换、成组改色快捷操作、识别完成后到合并前的草稿持久化（中途关页面即丢，重做不痛）。

## 与现有 PRD 的关系

intake → catalog 链路约束：

| intake 阶段 | catalog 端动作 |
|---|---|
| CUJ-1~4 草稿阶段 | 仅前端态，`data/catalog.yaml` 与 DB 均不受影响 |
| CUJ-5 备份阶段 | 把现有 `data/catalog.yaml` 复制到 `data/catalog.yaml.bak.<时间戳>` |
| CUJ-5 写入阶段 | append 到 `data/catalog.yaml`（保持中文键、保持文件 YAML 合法） |
| CUJ-5 reload 阶段 | 复用 prd-000 CUJ-2 的 `load_catalog(db)` 链路（不调用 `POST /api/catalog/reload`，而是在合并端点内部直接调用 `load_catalog`，避免一次额外往返） |
| CUJ-5 任一步失败 | 从备份文件恢复 `data/catalog.yaml`，并把草稿原样保留在前端（用户回到上一步） |

命名约定（用户明确指定，与现有 `data/catalog.yaml` 风格一致，参见 `data/catalog.yaml.example` 中如「转角书桌-下桌」的现有数据）：

- 组件命名 = `<产品基名>-<组件名>`，例如「床头柜-侧板」「床头柜-抽屉」
- 打印盘命名 = `<组件名>-<件数>`，例如「床头柜-侧板-2」「床头柜-抽屉-3」「床头柜-隔板大-9」
- 产品命名 = `<产品基名> - <配色变体名>`，例如「床头柜 - 灰白」「床头柜 - 黑粉」 — 每个配色变体合并后是 catalog 中一条独立的 `产品` 条目，BOM 完全相同，仅每行的「颜色」字段不同

## 数据流

```
用户拖入截图           ──────►  CUJ-1 启发式分类（assembly / produce）
                                  │
                                  ▼
                              CUJ-2 LLM 识别（DeepSeek，单 provider，架构留扩展位）
                                  │
                                  ▼
                              CUJ-3 草稿校对（BOM 件数 + 打印盘件数/耗时 + 撞名 surface）
                                  │
                                  ▼
                              CUJ-4 颜色矩阵（N 个平等配色变体）
                                  │
                                  ▼
                              CUJ-5 合并预览 → 备份 + append + load_catalog(db) → 成功/失败
                                                                                    │
                                                              成功 ──► /products 已可见新产品
                                                              失败 ──► 从 bak 文件恢复，草稿保留
```

## 启发式分类规则（CUJ-1 / CUJ-2 / CUJ-3 共用）

为节省 LLM token，**类别判定不走 LLM**：

- **打印盘截图（produce）**：图像右侧约 1/3 宽度存在切片软件的耗材面板（耗材色块列 + 「总时间」字段）— 按区域颜色直方图启发式判定。
- **组装图（assembly）**：不含右侧切片面板。通常是产品的多角度装配示意或爆炸图，主体居中 / 占满画幅。

LLM 不读截图右下角的盘号编号（拓竹切片软件的「01/03/04」），盘号系统按命名约定生成，避免 LLM 把切片软件 UI 上的元数据误读为产品数据。LLM 不推断颜色（截图里的灰色是切片软件的默认材质色，不是组装颜色）。

## CUJ-1：上传截图 + 自动分类

**Dependencies**: 无（本 PRD 第一步；前置依赖 prd-000 已存在 `data/catalog.yaml`，作为撞名比对的基准）
**Priority**: P0（intake 链路入口）

### Context

作坊主在拓竹切片软件里完成产品建模后，会得到一组截图：多张产品组装示意图 + 每个打印盘的切片预览。本 CUJ 让用户把这组截图一次性拖入，由系统自动分到「组装图」「打印盘」两栏，作为后续 LLM 识别的输入。系统不强求用户预先归类（启发式判定会替他做），但保留人工纠正的手段（拖动调类、删除、追加），让用户对输入保持完全控制。

### Preconditions

- 后端已启动，根目录 `.env` 中已配置 `DEEPSEEK_API_KEY`（否则进入禁用态，见边界）。
- 用户已在浏览器打开前端，左侧导航菜单加载完成。
- `data/catalog.yaml` 存在（用于 CUJ-3 的撞名比对，本步不读）。

### Journey Steps

1. **User action**: 点击左侧导航菜单中的「产品录入」项（图标 `ScanOutlined`，第 3 项，位于「产品目录」之下、「订单管理」之上）。
   - **System response**: 路由切换到 `/intake`，渲染 intake 页面入口（CUJ-1 状态）。前端读取 `.env` 配置状态接口（如 `GET /api/intake/provider-status`）确认 `DEEPSEEK_API_KEY` 是否就绪。
   - **User sees**: 左侧菜单「产品录入」项高亮（`selectedKeys` 命中 `/intake`）。右侧内容区顶部一行：左侧标题「产品录入」（`<h2>`，`margin:0`），右侧步骤指示器（① 上传截图 → ② 识别 → ③ 校对 → ④ 颜色 → ⑤ 合并，当前 ① 高亮）。标题下方一行灰色提示文字：「拖入拓竹切片软件的截图，系统会自动识别 BOM、打印盘件数与耗时」。
   - **Details**: 步骤指示器在 CUJ-1~5 中保持可见，是用户对自己「走到哪一步」的唯一锚点。

2. **User action**: 在顶部「产品基名」输入框填入产品基名（如「床头柜」）— 也可留空，等 LLM 识别后自动推断填入。
   - **System response**: 仅前端态；输入框旁有 placeholder「如：床头柜（识别后可自动推断填入，也可现在手填）」。
   - **User sees**: 产品基名输入框占位文案可见；下方分割线下方是上传区。
   - **Details**: 产品基名是后续所有组件、打印盘、产品命名的前缀（如「床头柜-侧板」「床头柜-侧板-2」），CUJ-3/CUJ-4 中会拼接显示。

3. **User action**: 把 N 张截图（混合 assembly + produce，无需预排序）一次性拖入中央大型 dropzone（虚线边框，提示文字「拖入截图 或 选择文件…」）。也可点击「选择文件…」 secondary 按钮通过系统文件选择器多选。
   - **System response**: 前端逐张读取文件 → 生成缩略图 → 对每张图运行**启发式分类**（见「启发式分类规则」段）→ 自动归到对应栏。每张图上传中显示 spinner 蒙层 + 顶部 mini dropzone 旁文案「上传中 9 / 14」蓝字进度。
   - **User sees**: dropzone 区域消失，主区切换为**左右两栏布局**：
     - 左栏「**组装图**」：淡蓝底 `#f5faff` + 蓝点 `#1677ff` 标识。栏头显示「组装图 · 3 张」+ 一行说明「产品多角度装配示意 / 爆炸图，用于推断 BOM」。
     - 右栏「**打印盘**」：淡橙底 `#fffaf0` + 橙点 `#fa8c16` 标识。栏头显示「打印盘 · 8 张」+ 一行说明「拓竹切片软件每个打印盘的预览，用于推断每盘件数与耗时」。
     - 两栏视觉差异强烈，用户不会混淆。每栏内是缩略图网格（约 120px × 80px，3 列），缩略图右上角有「×」删除 icon、右下角有「移到另一栏」拖动 handle。
     - 顶部一直显示一个 mini dropzone「+ 继续拖入截图」（窄条状，仅在主上传完成后出现），用户可随时追加。
   - **Details**: 启发式判错的图（如系统把组装图误归到 produce 栏），用户长按缩略图后可拖到另一栏 — 拖动期间另一栏边框高亮（drop target 提示）。

4. **User action**:（可选）拖动某张缩略图从一栏到另一栏，或点缩略图右上角「×」删除，或继续拖入新的截图。
   - **System response**: 前端态变更，栏头张数同步更新。
   - **User sees**: 缩略图实时移动 / 删除 / 追加；栏头计数实时变化（如「组装图 · 3 张」变「组装图 · 4 张」）。
   - **Details**: 拖动有 200ms 缓动动画；删除前不二次确认（误删可重新拖入，代价低）。

5. **User action**: 检查左右两栏数量正确后，点击右下角「开始识别」primary 按钮。
   - **System response**: 进入 CUJ-2（识别中状态）。已上传的图与产品基名作为前端态保留，便于失败时回退。
   - **User sees**: 按钮在「assembly 数 ≥ 1 且 produce 数 ≥ 1」时点亮（AntD primary 蓝），否则灰且 hover 显示 tooltip 「需至少 1 张组装图 / 打印盘截图」；按钮旁有 inline hint 文字同样提示。
   - **Details**: 「开始识别」是 LLM token 消耗的唯一触发点 — 上传过程本身不调用 LLM，用户对何时花 token 有完全控制。

### Edge Cases & Error States

- **`.env` 未配置 `DEEPSEEK_API_KEY`**：进入页面时检测失败，整页禁用 — 上传区遮罩、产品基名输入框 disabled、「开始识别」按钮永远灰。顶部展示红色 AntD `Alert` 「未检测到 LLM 提供商 API key」+ 描述「请在项目根目录 `.env` 文件中配置 `DEEPSEEK_API_KEY`，参见 `.env.example`。配置后重启后端服务」（措辞保持 provider-agnostic 友好，未来加 provider 时不改文案）。
- **空态（用户进入页面但未上传任何图）**：主区显示大型 dropzone（虚线边框，`min-height: 360px`），居中显示提示插画 + 文案「拖入截图 或 选择文件…」+ 灰色副文案「支持一次拖入多张，可混合组装图与打印盘截图，系统会自动归类」。
- **只有一栏有图（assembly 0 张或 produce 0 张）**：「开始识别」按钮 disabled。空栏内显示 placeholder 区域 + 文案「此栏暂无截图，请拖入或继续上传」+ 旁边一个细线箭头指向另一栏，提示「也可从另一栏拖一张过来」。
- **图很多（每栏 30+ 张）**：每栏内部固定 `max-height: 380px` + 内部独立滚动条，整体页面不被撑高。栏头张数计数始终可见（粘性 sticky）。
- **上传中**（多张大图并发上传）：每张未完成的缩略图带半透明蒙层 + 中心 spinner；顶部 mini dropzone 旁显示「上传中 9 / 14」蓝字进度。上传完成前「开始识别」按钮仍按数量条件判断（已成功上传的张数）。
- **某张图上传失败**（如文件损坏、超出大小限制）：该缩略图位置显示红色边框 + 「上传失败 · 重试」按钮；其他图正常落位，不阻塞流程。
- **启发式分类错误**：见 Journey Step 4 — 用户手动拖动调类。系统不会在用户调过类后再次「自动归类」覆盖用户决定。
- **非图片文件被拖入**（如 PDF / 文本文件）：前端文件类型校验，拒绝该文件并顶部弹 `message.warning`「仅支持图片文件（JPG / PNG / WebP）」。
- **页面刷新 / 关闭**：所有上传内容与产品基名丢失（MVP 不持久化草稿，重做不痛）。再次进入页面是 CUJ-1 空态。

## CUJ-2：触发 LLM 识别

**Dependencies**: CUJ-1（输入：已分类的 assembly / produce 截图 + 可选的产品基名）
**Priority**: P0（intake 链路的核心一步；失败则无法进入校对页）

### Context

CUJ-1 攒齐了输入素材，本 CUJ 把它们交给 LLM，识别出每张组装图能推断的 BOM 件数、每张打印盘的件数与耗时、组件名、产品基名（如果用户没填）。识别是异步过程（DeepSeek 单次请求约 20 ~ 40 秒），中途用户能感知进度且能取消；失败时用户能看到具体错误并选择重试或返回上一步调整图。

### Preconditions

- CUJ-1 已完成：assembly ≥ 1、produce ≥ 1、`.env` 中 `DEEPSEEK_API_KEY` 就绪。
- 后端已实现 `POST /api/intake/recognize` 端点（请求体含图列表 + 产品基名，响应是识别后的草稿结构）。
- DeepSeek API 可达（局域网代理 / 直连均可，取决于部署环境）。

### Journey Steps

1. **User action**: 在 CUJ-1 点击右下角「开始识别」primary 按钮。
   - **System response**: 主区切换为识别进度页（CUJ-2 状态），页面标题加状态后缀「产品录入 · 识别中」（让浏览器 tab 标题反映状态）。步骤指示器移动到 ②。前端 `POST /api/intake/recognize`，请求体含 `{ 产品基名, assembly_images: [...], produce_images: [...] }`。后端将每张图按既定 prompt 模板调用 DeepSeek，汇总响应、解析、构造草稿数据。
   - **User sees**: 中央一张大卡片（白底圆角 8px、阴影），顶部主标题「正在识别 N 张图片…」（N = assembly + produce 张数），下方副标题「完成后会自动跳转到草稿预览页」。卡片中部一行灰色元信息：`产品基名：床头柜  ·  组装图 3 张  ·  打印盘 8 张`（让用户最后一次确认在处理的是刚才上传的内容）。
   - **Details**: MVP 用粗粒度三阶段灯，不上 server streaming，后端按图轮询调用或批量调用都可。

2. **User action**: 等待识别完成（通常 20 ~ 40 秒）。
   - **System response**: 后端在三个粗阶段间推进，前端轮询（或前端按时间近似推进，MVP 可接受 — 状态灯只是体感工具，不要求与后端严格同步）：① 上传图片（已完成，✓ 绿勾） → ② 调用 LLM 识别（pulse 动画蓝点，进度条从 30% 渐进到 80%） → ③ 解析返回数据。
   - **User sees**: 三阶段灯进度指示器水平排列。下方进度条（线性渐变，蓝 `#1677ff`，宽度从 30% 渐进到 95%）+「约 30 秒，请稍候…」文案。中央「取消」 secondary 按钮（用户随时可中止）。底部小字 tip：「识别期间请勿关闭页面。如果耗时超过 2 分钟仍未完成，可能是网络问题或 LLM 服务异常，可点击取消后重试」。
   - **Details**: 进度条不能回退；解析阶段最快（< 200ms），用户通常看不到第三个灯独立活跃。

3. **User action**:（成功分支）等到后端返回 `{ ok: true, draft: {...} }`。
   - **System response**: 前端把 draft 落到 CUJ-3 状态，**自动跳转**到 CUJ-3 草稿校对页（无独立 success 帧 — 用户已经等了 30 秒，不需要再点「确认」）。
   - **User sees**: 主区切换到 CUJ-3（详见下一节）。页面标题变为「产品录入 · 草稿校对」。
   - **Details**: 跳转前不展示中间态，避免用户多余等待感。

4. **User action**:（取消分支）在识别中点击「取消」按钮。
   - **System response**: 前端发出 abort signal（`fetch` 携带的 `AbortController`），后端收到中止；前端退回 CUJ-1 状态。
   - **User sees**: 主区切回 CUJ-1，左右两栏图与产品基名**完整保留**（取消代价为 0）。
   - **Details**: 取消已发出但未完成的 LLM 调用不退还 token（DeepSeek 不支持中途退费），文案中暂不强调这点（避免吓阻用户随手取消）；token 浪费由用户的「显式开始识别」按钮已经过滤。

5. **User action**:（失败分支）后端返回 `{ ok: false, error: "..." }` 或网络错误。
   - **System response**: 前端切换到错误卡片状态（仍在 CUJ-2 页面，不退回 CUJ-1）。
   - **User sees**: 中央卡片改为错误状态 — 红色 `!` 图标 + 标题「LLM 识别失败」+ 描述「已上传的图片仍保留在上一步，可调整后重试」+ 等宽字体（`font-family: monospace`）的错误详情块（如 `HTTP 401 Unauthorized — DeepSeek 拒绝请求，可能是 API key 无效或已用尽额度` / `连接超时 — 30 秒未收到响应，请检查网络` / `响应解析失败 — 返回内容不是预期的 JSON 结构`）。底部两个按钮：「返回上一步」（secondary，退回 CUJ-1 保留所有图） / 「重试」（primary，直接重新触发识别）。
   - **Details**: 错误详情对用户直接可见 — 这是技术作坊主自用产品，原始错误信息比包装过的笼统文案更有价值。

### Edge Cases & Error States

- **`.env` 配了 API key 但密钥失效**（HTTP 401）：错误详情段显示「`HTTP 401 Unauthorized — DeepSeek 拒绝请求，可能是 API key 无效或已用尽额度`」；用户的处理路径：去 DeepSeek 控制台核对 → 改 `.env` → 重启后端 → 回本页重试。
- **网络超时**（30+ 秒无响应）：前端在 90 秒后主动 abort，文案显示「`连接超时 — 90 秒未收到响应，请检查网络`」。
- **LLM 返回非预期格式**（如返回了 markdown 包装的 JSON、或字段缺失）：后端解析层负责剥离 markdown + JSON schema 校验，失败时返回「`响应解析失败 — 返回内容不是预期的 JSON 结构`」并把原始响应片段截断到 200 字符附在错误详情后（供用户判断是否是 prompt 退化）。
- **DeepSeek 服务降级 / 5xx**：错误详情段显示「`HTTP 503 Service Unavailable — DeepSeek 服务暂时不可用，请稍后重试`」。
- **图片过大被 DeepSeek 拒绝**：后端在上传到 DeepSeek 前应做大小校验 / 压缩（设计 hook，本 PRD 不展开），若仍透出，错误详情显示「`图片过大 — 单张图超过 LLM 接受的最大尺寸，请缩小后重试`」。
- **用户在识别中关闭浏览器**：后端无能力中止已发出的 LLM 调用，token 消耗已发生；前端再次进入 `/intake` 是 CUJ-1 空态（不恢复识别结果，MVP 不持久化草稿）。
- **取消后立刻又点开始识别**：允许，无去重逻辑；按 LLM 调用计费。

- `docs/ux/prd-005-intake/cuj-2-error.html` — 识别失败（HTTP 401 错误详情示例）

## CUJ-3：草稿校对 BOM + 打印盘

**Dependencies**: CUJ-2（输入：LLM 识别出的草稿结构 — 组件列表、件数、打印盘列表、每盘件数、耗时）
**Priority**: P0（LLM 识别难免错，校对是写入 catalog 前的最后一道护栏）

### Context

LLM 把图像识别成结构化草稿，但件数和耗时是关键校对项 — 错一个就让 catalog 长期带 bug。本 CUJ 让用户对照原图核对每个组件件数、每张打印盘的件数与耗时；同时**提前**在本步骤暴露与现有 catalog 的撞名（不留到 CUJ-5 写入失败才发现），让用户改名或确认。组件命名与盘号命名按既定规则填默认值，用户可改。

### Preconditions

- CUJ-2 已成功完成，前端持有 draft 数据：`{ 产品基名, 组件列表: [{名称, 装配件数}], 打印盘列表: [{盘号, 所属组件, 单盘件数, 耗时, 原图引用}] }`。
- assembly 缩略图与每张 produce 缩略图在前端仍可访问（CUJ-1 上传后保留至 CUJ-5 合并成功）。
- 后端已暴露撞名检测接口（如 `POST /api/intake/check-conflicts`，输入草稿，输出撞名列表）。

### Journey Steps

1. **User action**: CUJ-2 识别成功后自动进入本页（无主动操作）。
   - **System response**: 主区渲染草稿校对页（CUJ-3 状态），页面标题加后缀「产品录入 · 草稿校对」。步骤指示器移到 ③。前端并发触发撞名检测接口。
   - **User sees**: 页面顶部「产品基名」输入框，已被 LLM 推断填入（如「床头柜」），可改。下方两张卡片纵向排列：「组件清单 (BOM)」与「打印盘清单」。底部一行两个按钮：「← 上一步：调整截图」（secondary） / 「下一步：填写颜色 →」（primary）。
   - **Details**: 产品基名变更会**即时同步**到下方所有组件名 / 盘号的前缀（如把「床头柜」改成「斗柜」，所有组件名前缀自动跟随，前提是用户未手动改过该字段）— 但已手改过的字段保留用户值不被覆盖。

2. **User action**: 浏览「组件清单 (BOM)」卡片。
   - **System response**: 无；纯展示。
   - **User sees**:
     - 卡片标题「组件清单 (BOM)」+ 下方一行 assembly 缩略图横排（3 张可见，每张 64×48px，hover 显示放大镜 🔍 icon，点击右侧滑出 drawer 显示大图，便于对照核对）。
     - 缩略图下方是表格，**只两列**：
       - 「**组件名**」：可编辑 text input，默认值带产品基名前缀（如「床头柜-侧板」「床头柜-抽屉」「床头柜-隔板大」）。每行组件由 LLM 从多角度组装图推断件数。
       - 「**装配件数**」：可编辑 number input，**关键校对项**，蓝色高亮样式：`border-color: #bfdfff` + `background: #fafdff` + 字体粗 600 + 文字色 `#1677ff`，强化「这是要校对的字段」。
     - 表格下方一个虚线按钮「+ 增加组件」，用户可手补 LLM 漏掉的组件。

3. **User action**: 浏览「打印盘清单」卡片。
   - **System response**: 无；纯展示。
   - **User sees**: 卡片标题「打印盘清单」+ 下方表格，**5 列**：
     - 「**盘号**」：可编辑 text input，默认值由系统按命名约定拼接（如「床头柜-侧板-2」「床头柜-抽屉-3」「床头柜-隔板大-9」「床头柜-隔板大-12」），盘号编号不读拓竹切片软件 UI 上的「01/03/04」。
     - 「**所属组件**」：AntD `Select` 下拉，选项是「组件清单」表里所有组件名；用户在 BOM 表里改组件名时此下拉同步更新选项。
     - 「**单盘件数**」：可编辑 number input，**关键校对项**蓝色高亮（同 BOM 件数样式）。
     - 「**耗时**」：可编辑 text input，**关键校对项**蓝色高亮，格式接受 `2h43m` 或 `17m45s`，由 LLM 从盘截图右侧面板「总时间」字段读取。input 失焦时做格式校验，非法格式红边 + tooltip「格式应为 `2h43m` 或 `17m45s`」。
     - 「**原图复核**」：每行一个 icon button（眼睛 `👁`），点击右侧滑出 drawer 显示该盘原图大图 + LLM 识别的元数据（识别到的件数、耗时）+ 一个件数 number input + 「应用到本行」「取消」两个按钮。
   - **Details**: 表格下方一个虚线按钮「+ 增加打印盘」，用户可手补 LLM 漏掉的盘。

4. **User action**: 校对件数和耗时，发现 LLM 把某盘件数从 12 看成了 2，点击该行「原图复核」👁 icon。
   - **System response**: 右侧滑出 AntD `Drawer`（宽 480px），显示该盘原图（最大化、保留宽高比，下方显示 LLM 识别的元数据 + 一个件数 input + 「应用到本行」「取消」按钮）。
   - **User sees**: Drawer 内大图清晰可读拓竹切片软件右侧面板上的「总时间」与盘内件数，用户可对照修正。
   - **Details**: drawer 是对照工具，不强制用户在 drawer 内改值 — 也可关掉 drawer 后直接在主表格行内 input 中改。

5. **User action**: 用户改完件数后点 drawer 内「应用到本行」（或直接关 drawer 后在主表内改）。
   - **System response**: 前端态更新该行件数；drawer 关闭。
   - **User sees**: 该行件数 input 显示更新后的值；蓝色高亮样式持续提示这是关键字段。
   - **Details**: 改件数**不会**自动改盘号尾缀（如「床头柜-隔板大-9」改件数为 12 后，盘号仍是「床头柜-隔板大-9」直到用户手动改 ）— 避免用户主键被自动覆盖。

6. **User action**:（撞名分支）顶部红色 alert 提示「检测到 2 处与现有目录重名 — 请改名或确认合并」。用户点击其中一行查看冲突。
   - **System response**: 撞名行整体浅红背景 `var(--red-soft)`、对应 input 红边、行内右侧出现红字提示「目录中已存在同名『床头柜-侧板』」。
   - **User sees**: 红 alert 描述说明撞名原因（通常是用户二次导入同一产品 — 「这通常意味着这个产品已经录入过，可能是重新识别」）；问题行视觉上明显红化；用户改名（如「床头柜2-侧板」）后该行红色样式即时消除。
   - **Details**: 撞名是按「产品基名 + 组件名 + 盘号 + 配色变体名」与现有 `data/catalog.yaml` 比对，比对逻辑由后端撞名接口实现。改名解除冲突是即时反馈，不需要再点撞名检测。

7. **User action**: 校对完成，点击底部「下一步：填写颜色 →」按钮。
   - **System response**: 进入 CUJ-4。前端把校对后的草稿带入下一步。
   - **User sees**: 主区切换到 CUJ-4 颜色矩阵；页面标题变为「产品录入 · 填写颜色」。
   - **Details**: 如果撞名未解决（仍有红行），按钮 disabled + tooltip「请先解决撞名冲突再继续」。

### Edge Cases & Error States

- **LLM 漏识别某组件**：BOM 表里该组件不出现，用户点「+ 增加组件」手补，并对应在「打印盘清单」表里改某些行的「所属组件」下拉。
- **LLM 把件数识错**：用户改对应行件数 input；蓝色高亮是为这个常见情况设计的。
- **LLM 把耗时识错**：用户改耗时 input；格式校验失败时红边 + tooltip。
- **LLM 把同一组件识成两条**（如「床头柜-侧板」「床头柜-侧板-」末尾多空格）：用户在 BOM 表里删一条（行右侧 `×` icon），剩下那条调整件数；同时「打印盘清单」表里该删掉的组件不再出现在「所属组件」下拉里，已选用它的行变成空白下拉 → 红字提示「组件不存在，请重新选择」。
- **撞名未解决就点下一步**：按钮 disabled，hover tooltip「请先解决撞名冲突再继续」。
- **用户把 BOM 全删空**：「下一步」按钮 disabled + tooltip「至少需要 1 个组件」。
- **用户把打印盘全删空**：允许（理论上产品也可以只有 1 个组件、不需要打印盘 — 但实际罕见）；不强制 disabled，但底部 hint 文字「当前没有打印盘，确认合并后该产品在排班时不会产生任何打印批次」。
- **盘号重复**（用户改名后两个盘叫同一个名字）：在本页即时校验，重复的盘号 input 红边 + tooltip「盘号在本草稿内不可重复」，「下一步」按钮 disabled。
- **耗时为 0 / 负数 / 空**：input 红边 + tooltip「耗时不可为空 / 必须大于 0」。
- **件数为 0 / 负数 / 空**：input 红边 + tooltip「件数必须大于 0」。
- **「原图复核」drawer 内用户改值后未点应用直接关 drawer**：drawer 内修改丢弃（不污染主表格）；主表格行内 input 仍可直接改。
- **assembly 缩略图横排超过 3 张**：横向滚动 + 右侧渐变蒙层提示「可滚动查看更多」。
- **撞名检测接口本身失败**：顶部黄色 warning alert「撞名检测失败，合并时会再次检测；建议手动核对产品基名」；不阻塞下一步（CUJ-5 服务端兜底再扫一遍）。

- 改名解除撞名后红色样式即时消除（无需再次点撞名检测）。
- 耗时格式非法（既不是 `Xh Ym` 也不是 `Xm Ys`）时 input 红边 + tooltip「格式应为 `2h43m` 或 `17m45s`」，「下一步」按钮 disabled。
- 件数为 0 / 负数 / 空时 input 红边 + tooltip「件数必须大于 0」，「下一步」按钮 disabled。
- 盘号在本草稿内重复时 input 红边 + tooltip「盘号在本草稿内不可重复」，「下一步」按钮 disabled。
- 底部按钮「← 上一步：调整截图」（secondary，点击退回 CUJ-1 保留所有图与已校对的产品基名） / 「下一步：填写颜色 →」（primary）。
- 「下一步」按钮在撞名未解决 / BOM 为空 / 任一关键字段非法时 disabled，hover tooltip 说明原因。

## CUJ-4：颜色矩阵 + 多配色变体

**Dependencies**: CUJ-3（输入：校对后的 BOM + 打印盘草稿）
**Priority**: P0（每个配色变体合并后是 catalog 中一条独立 `产品` 条目；没填颜色就不能合并）

### Context

同一产品常有多种配色变体（如床头柜的「灰白」「黑白」「黑粉」），每个变体的 BOM 完全相同但每行的颜色不同。手填 `catalog.yaml` 时用户要把整套 BOM 重复 N 遍只为改颜色 — 极易抄错。本 CUJ 把颜色填写设计成「行 = 组件 × 列 = 变体」的矩阵，复制一列即可基于已有变体克隆出新变体。颜色由用户手动输入（不让 LLM 推断），但提供「本产品已用过的颜色」「11 个常用色」「自由输入」三段快捷方式，让重复劳动最小化。

### Preconditions

- CUJ-3 已通过校对（BOM 至少 1 个组件、所有关键字段合法、无未解决撞名）。
- 前端持有 draft：`{ 产品基名, 组件列表, 打印盘列表, 配色变体: [{变体名, 颜色矩阵}] }`，初始有 1 个空白变体。

### Journey Steps

1. **User action**: CUJ-3 点击「下一步：填写颜色」进入本页。
   - **System response**: 主区渲染颜色矩阵页（CUJ-4 状态），页面标题加后缀「产品录入 · 填写颜色」。步骤指示器移到 ④。
   - **User sees**: 主区中央一张大卡片，标题「颜色矩阵」+ 副标题「为每个配色变体的每个组件指定颜色。合并后每个变体是 catalog 中一条独立产品条目」。下方矩阵表格 + 底部「可选颜色」汇总条 + 底部按钮行。
   - **Details**: 矩阵初始 1 列变体「床头柜 - 配色 1」（系统默认命名，用户可改）。

2. **User action**: 浏览矩阵结构。
   - **System response**: 无；纯展示。
   - **User sees**:
     - 矩阵列结构：**第 1 列**「组件名」（来自 BOM）+ **第 2 列**「件数」（`×2` `×4` `×6` 样式灰色小字）+ **第 3 列起**每列是一个配色变体 + **最后一列**「+ 新增配色」（独立、rowspan 跨满表格高度、点击在矩阵末尾追加一个空白变体列）。
     - 每列变体头（第 3 列起）：变体名 input（如「床头柜 - 灰白」，用户可改）+「⎘ 复制此列」按钮（点击在右侧克隆出一列、所有 cell 预填克隆值，便于在已有变体基础上微调几个颜色就成新变体）+「× 删除此变体」按钮（只有 1 列时隐藏，避免误操作删光）。
     - 每个矩阵单元格是「**color cell**」：左侧 16px 色块 swatch（按色名映射到背景色，色名未知时显示斜纹底纹 45° 灰白条纹 + 浅色「选择颜色」文案）+ 中间色名 + 右侧 `▾` 箭头（暗示可下拉）。

3. **User action**: 点击某个 color cell（如「床头柜-侧板 × 配色 1」对应的格子）。
   - **System response**: 浮出 popover（位置：cell 正下方，AntD `Popover` 风格、白底圆角阴影、宽 320px）。
   - **User sees**: popover 内三段结构纵向排列：
     - **第 1 段**：标题「本产品已用过的颜色」+ 横排 chip 列表（每个 chip：16px 色块 + 色名文字 + 圆角 4px 蓝边框，点选直接应用到当前 cell 并关闭 popover）。空时本段隐藏（首次进入本页时第一段为空）。
     - **第 2 段**：标题「常用颜色」+ 横排 11 个 chip：白 / 黑 / 灰 / 棕 / 粉 / 红 / 黄 / 蓝 / 绿 / 橙 / 紫（chip 样式同上，色块用对应实际色值），点选直接应用。
     - **第 3 段**：标题「输入新颜色名」+ 文本 input（placeholder「如：浅木色」）+ 「添加」secondary 按钮。添加后该色名自动进入「本产品已用过的颜色」段（供同一产品其他 cell 复用）+ 应用到当前 cell + 关闭 popover。
   - **Details**: 所有色名都是**中文字符串**（写入 `catalog.yaml.组件.可选颜色` 字段为字符串数组，与现有 catalog 命名风格一致 — 见 `data/catalog.yaml.example`）。色名是自由文本，无标准化也无颜色取色器（用户的口径 = 用户的口径，与 prd-000-catalog Open Questions §6 已知问题保持一致）。

4. **User action**: 给「配色 1」列的每一格选好颜色（例如所有侧板/抽屉/隔板设为「灰白」，把手设为「灰白」）。
   - **System response**: 每次选完一格，前端态更新；当前 cell 的 swatch 显示对应颜色色块、色名文字显示。
   - **User sees**: 整列填满后，最下方的「可选颜色」汇总条出现「灰白」chip。
   - **Details**: 同列内所有 cell 填的色可以相同（用户的一个变体可以全是灰白），也可以不同（如门是黑色其余是灰白）。

5. **User action**: 想加第二个变体「床头柜 - 黑白」，点击「配色 1」列头的「⎘ 复制此列」按钮。
   - **System response**: 在矩阵末尾追加一列，变体名默认「床头柜 - 配色 2」，所有 cell 预填「配色 1」的值。
   - **User sees**: 新列出现在「+ 新增配色」之前，所有色块与「配色 1」一致。
   - **Details**: 「复制此列」是 MVP 阶段的多变体生成主路径 — 比从零开始填省事得多。

6. **User action**: 用户改新列的变体名为「床头柜 - 黑白」，并把几个 cell 改成「黑色」（点击 cell → popover → 「常用颜色」段点「黑」chip）。
   - **System response**: 每次改一个 cell，「可选颜色」汇总条同步更新（如「灰白」chip 旁出现「黑」chip）。
   - **User sees**: 第二列变体形成；汇总条增长。
   - **Details**: 「可选颜色」汇总条本质上是「本产品所有变体出现过的色名 dedupe」，对应 `catalog.yaml.组件.可选颜色` 字段（合并时各组件的可选颜色 = 该组件在所有变体中出现过的色名 dedupe，由 CUJ-5 合并逻辑生成）。

7. **User action**: 想再加第三个变体「床头柜 - 黑粉」，点击最右「+ 新增配色」列。
   - **System response**: 矩阵末尾追加一列空白变体，变体名默认「床头柜 - 配色 3」，所有 cell 显示斜纹「选择颜色」状态。
   - **User sees**: 新空白列出现。
   - **Details**: 「+ 新增配色」是从零起步路径（用户没有合适的 base 可复制时用）；「复制此列」是克隆路径（基于已有变体微调）。两种路径并存。

8. **User action**: 把所有变体的所有 cell 填齐颜色后，点击底部「下一步：合并 N 个产品条目 →」按钮（N = 变体数，如「合并 3 个产品条目」）。
   - **System response**: 进入 CUJ-5。
   - **User sees**: 主区切换到 CUJ-5 合并预览页。
   - **Details**: 「下一步」按钮 disabled 直到**至少有一个变体的所有 cell 都填齐颜色**（其他变体可以未填齐，但合并时只合并填齐的变体；MVP 简化：所有变体都填齐才可继续 — 见 AC）。文案动态显示当前已填齐的变体数。

### Edge Cases & Error States

- **首次进入本页，第 1 段「本产品已用过的颜色」为空**：popover 中该段隐藏，只显示「常用颜色」「输入新颜色名」两段。
- **用户输入色名包含特殊字符 / 换行符**：input 校验，过滤换行/前后空格；不限制其他字符（中文 / 英文 / 数字 / 标点都允许，作坊主自用产品不限制）。
- **变体名空白**：变体名 input 失焦时如为空，自动回填默认名「`<产品基名>` - 配色 N」。
- **变体名重复**：两个变体名一致时本页即时校验，第二个变体名 input 红边 + tooltip「变体名不可重复 — 合并后会撞 catalog 主键」，「下一步」按钮 disabled。
- **只有 1 列变体时**「× 删除此变体」按钮隐藏（避免删光）。
- **删除变体前不二次确认**：误删可立即「+ 新增配色」重做，代价低。
- **变体数 > 8**（用户连点「+ 新增配色」很多次）：矩阵横向滚动 + 列头粘性 sticky；性能预期足够（行 10~30、列 < 20）。
- **某些 cell 未填颜色但用户点了「下一步」**：按钮 disabled（不允许 cell 部分填齐）+ hover tooltip「请填齐所有 cell 的颜色」。
- **用户在第 3 段输入新色名「红色」但本产品已用过「红色」**：自动 dedupe，应用到 cell 后第 1 段仍只有一个「红色」chip。
- **删除一个变体后该变体唯一用到的色名是否从「可选颜色」汇总条移除**：是 — 汇总条始终是当前所有变体 cell 值的 union dedupe，删变体后实时重算。

### Mocks / Reference Designs

- 初始进入本页有 1 列变体，默认命名「`<产品基名>` - 配色 1」（如「床头柜 - 配色 1」），所有 cell 是空白斜纹底纹「选择颜色」状态。
- 每列变体头包含：变体名 input（可改）、「⎘ 复制此列」按钮、「× 删除此变体」按钮（仅 1 列变体时隐藏）。
- 「⎘ 复制此列」点击后在右侧克隆一列、所有 cell 预填克隆值。
- 「+ 新增配色」点击后在矩阵末尾追加 1 列空白变体，默认命名「`<产品基名>` - 配色 N」。

## CUJ-5：合并到 catalog.yaml

**Dependencies**: CUJ-4（输入：完整的草稿 — BOM + 打印盘 + 多配色变体的颜色矩阵）+ 复用 [prd-000-catalog](prd-000-catalog.md) CUJ-2 的 `load_catalog(db)` 链路
**Priority**: P0（intake 链路终点；这一步把草稿落到单一数据源 `data/catalog.yaml`）

### Context

草稿走完前 4 个 CUJ 已经完整 — 现在要把它转换为 `data/catalog.yaml` 的合法片段并 append 写入文件，再触发 `load_catalog(db)` 让 DB 镜像同步。这一步是高风险写操作：YAML 写坏或 `load_catalog` 失败都会让生产中的 catalog 损坏。本 CUJ 通过「**自动备份 + 失败自动回滚 + 写入前预览**」三重护栏让用户敢按下「确认合并」。成功后直接接通 prd-000 CUJ-2 的现有链路（不调 `POST /api/catalog/reload` 而是后端内部直接调用 `load_catalog(db)`），合并完成时 `/products` 页面已可见新产品。

### Preconditions

- CUJ-4 已完成：草稿包含至少 1 个变体、所有 cell 颜色填齐、变体名无重复。
- `data/catalog.yaml` 当前是合法 YAML 且可读写（用户对宿主机文件系统有写权限）。
- 后端已实现合并端点（如 `POST /api/intake/merge`，请求体含完整草稿，响应是合并结果）。
- 复用现有 `load_catalog(db)` 链路（实现见 `docs/design/design-catalog.md`）。

### Journey Steps

1. **User action**: CUJ-4 点击「下一步：合并 N 个产品条目 →」进入本页。
   - **System response**: 主区渲染合并预览页（CUJ-5 初始状态），页面标题加后缀「产品录入 · 合并到 catalog」。步骤指示器移到 ⑤。前端把草稿序列化为预览 YAML 字符串。
   - **User sees**: 主区两张卡片纵向排列：「合并摘要」「YAML 预览」。底部按钮行「← 上一步：填写颜色」（secondary） / 「确认合并并重新加载 →」（primary，带绿勾 svg 图标）。
   - **Details**: 本页**只展示预览**，不发任何写请求 — 用户对「即将写入什么」有完全可见性。

2. **User action**: 浏览「合并摘要」卡片。
   - **System response**: 无；纯展示。
   - **User sees**: 卡片标题「合并摘要」+ 下方 3 行列表：
     - ① 「N 个新组件」+ 名称列表（如「床头柜-侧板、床头柜-抽屉、床头柜-隔板大、床头柜-把手、床头柜-门板、床头柜-底板」）
     - ② 「M 张新打印盘」+ 总耗时合计（如「8 张新打印盘 · 总耗时 18h27m」）
     - ③ 「K 个新产品变体」+ 变体名列表（如「床头柜 - 灰白、床头柜 - 黑白、床头柜 - 黑粉」）
     - 摘要下方一行灰底说明条（`background: #fafafa` 圆角）：「合并前会自动备份到 `catalog.yaml.bak.<时间戳>`，合并成功后会自动触发『重新加载目录』 — 写入失败时会自动回滚到备份」（让用户对操作链路有预期）。

3. **User action**: 浏览「YAML 预览」卡片。
   - **System response**: 无；纯展示。
   - **User sees**: 卡片标题「YAML 预览」+ 下方暗黑代码块（`background: #1e1e1e`、白字、圆角 4px、`max-height: 520px` + 内部独立滚动），显示即将 append 到 `data/catalog.yaml` 末尾的完整 YAML 内容：
     - 首行注释 `# --- 床头柜 系列，由产品录入工具于 2026-06-14 21:30:15 追加 ---` 标记追加批次
     - 然后三段：`组件:` 块（列出本次新增的所有组件 + 各自的 `可选颜色` 数组）、`打印盘:` 块（盘号 / 组件 / 数量 / 耗时分钟）、`产品:` 块（N 个变体，每个变体 BOM 内容相同、颜色不同）
     - 全部使用中文键（与 `data/catalog.yaml.example` 一致）
     - syntax highlighting：键 `#9cdcfe` 蓝 / 字符串 `#ce9178` 橙 / 数字 `#b5cea8` 绿 / 注释 `#6a9955` 绿斜体
   - **Details**: 这段预览 = 后端实际 append 的内容（前端用同一序列化逻辑生成，避免「预览看到的与实际写入的不一致」）。

4. **User action**: 检查无误后点击「确认合并并重新加载 →」primary 按钮。
   - **System response**: 按钮进入 loading 态（转圈，不可重复点击）。前端 `POST /api/intake/merge`，请求体含完整草稿。后端按顺序执行：
     1. **撞名兜底校验**：再次扫描草稿与现有 catalog 的撞名（CUJ-3 应已 surface，但兜底）。若发现撞名 → 直接返回 `{ ok: false, error_kind: "conflict", details: [...] }`，**不**做后续步骤。
     2. **备份**：把 `data/catalog.yaml` 复制到 `data/catalog.yaml.bak.<时间戳>`（时间戳格式如 `20260614-213015`）。失败 → 返回 `{ ok: false, error_kind: "backup_failed", details: "..." }`。
     3. **append 写入**：把序列化后的 YAML 内容 append 到 `data/catalog.yaml` 末尾。写入后用 `yaml.safe_load` 验证整文件仍是合法 YAML — 若不合法（理论上不应发生）→ 从备份恢复 + 返回 `{ ok: false, error_kind: "yaml_invalid", details: "..." }`。
     4. **触发 reload**：直接调用 `load_catalog(db)`（同 prd-000-catalog CUJ-2 链路），不走 HTTP 往返。失败 → 从备份恢复 `data/catalog.yaml` + 返回 `{ ok: false, error_kind: "load_failed", details: "..." }`。
     5. **成功**：返回 `{ ok: true, stats: {组件: n, 打印盘: m, 产品变体: k}, backup_path: "data/catalog.yaml.bak.20260614-213015", timing_ms: {写入: 12, 重新加载: 130} }`。
   - **User sees**: 「确认合并并重新加载」按钮显示加载转圈；其他按钮 disabled。
   - **Details**: 合并端点采用「文件级备份 + 失败回滚」语义。回滚操作是把 `.bak.<时间戳>` 复制回 `data/catalog.yaml`（不删 bak 文件，保留作为审计）。`load_catalog(db)` 内部失败时 DB 是否完整回滚由现有实现决定，参考 prd-000-catalog Open Questions §2。

5. **User action**:（成功分支）等到后端返回 `{ ok: true, ... }`。
   - **System response**: 前端切换到成功页（CUJ-5 成功状态），页面标题加后缀「产品录入 · 完成」。
   - **User sees**: 主区中央大卡片，绿色大 `✓` 图标 + 标题「合并成功」+ 描述（「已向 `data/catalog.yaml` 追加 N 个组件、M 张打印盘、K 个产品变体，目录已自动重新加载，可立即使用」）。下方 2 行元信息：
     - 备份文件名：等宽字体显示 `data/catalog.yaml.bak.20260614-213015`
     - 耗时分项：等宽字体显示 `写入 12 ms · 重新加载 130 ms`
     底部两个按钮：「继续录入下一个产品」（secondary，点击回到 CUJ-1 空态、清空所有前端态） / 「前往产品目录查看 →」（primary，跳到 `/products` 让用户看到新加的产品已在目录里 — 验证 prd-000 CUJ-1 已能看到新产品）。
   - **Details**: 跳转到 `/products` 后用户看到的产品列表是新一次 `load_catalog(db)` 同步后的结果，「床头柜 - 灰白」等变体已在产品列表中可见。

6. **User action**:（失败分支）后端返回 `{ ok: false, error_kind: "...", details: "..." }`。
   - **System response**: 前端切换到失败页（CUJ-5 失败状态），页面标题加后缀「产品录入 · 合并失败」。**草稿前端态保留**（用户可回上一步调整）。
   - **User sees**: 主区中央大卡片，红色大 `!` 图标 + 标题「合并失败 — 已自动回滚」（「已回滚」放标题里减少用户慌乱）+ 描述（措辞按 error_kind 变化，如 `load_failed` 时显示「重新加载 `data/catalog.yaml` 时检测到错误。文件已从备份恢复到合并前状态，你的草稿仍保留在上一步」）+ 等宽字体显示错误详情块（4 行布局）：
     ```
     错误类型: load_failed
     错误信息: 打印盘 '床头柜-侧板-2' 引用了不存在的组件 '床头柜-侧板X'
     已回滚至: data/catalog.yaml.bak.20260614-213015
     建议: 请回到上一步检查盘号与组件名是否一致
     ```
     底部两个按钮：「查看后端日志」（secondary，弹出 `Modal` 展示最近 100 行后端日志，便于用户排查 — 简单 textarea readonly） /「返回上一步调整」（primary，退回 CUJ-4，保留所有变体与颜色填写）。
   - **Details**: error_kind 决定描述措辞和建议文案：
     - `conflict`：「检测到与现有目录撞名（CUJ-3 应已提示）」+ 建议「请回到 CUJ-3 改名后重试」
     - `backup_failed`：「无法创建备份文件」+ 建议「请检查 `data/` 目录写权限」
     - `yaml_invalid`：「写入后整文件不是合法 YAML」+ 建议「请联系开发者排查序列化逻辑」
     - `load_failed`：「load_catalog 抛错」+ 建议根据具体错误信息提示

### Edge Cases & Error States

- **`data/catalog.yaml` 文件正被另一个进程读**：备份步骤可能瞬间冲突；重试通常即可解决（用户点「返回上一步调整」后再点「确认合并」）。
- **备份成功但 append 写入时磁盘满**：`yaml_invalid` 校验前可能就 `IOError`；归到 `backup_failed` 之后的统一异常处理，从备份回滚 `data/catalog.yaml`，返回 `{ ok: false, error_kind: "write_failed", details: "..." }`。
- **`load_catalog(db)` 部分成功 / 部分失败**：参考 prd-000-catalog Open Questions §2，DB 事务未显式 rollback 行为存在；本 PRD 不修复这个底层问题，但**文件层面**一定会从 bak 恢复，因此即便 DB 状态不一致，用户下次重启后端 / 主动点 prd-000 CUJ-2 的「重新加载目录」可重新同步到正确状态。
- **撞名兜底再次发现冲突**（CUJ-3 撞名检测有 bug 漏判 / 用户在 CUJ-3 撞名检测后又改名导致新撞名）：返回 `{ ok: false, error_kind: "conflict" }`，**未做文件写入**（备份也未发生 — 撞名校验在备份步骤之前）。失败页描述措辞「检测到与现有目录撞名」+ 建议「请回到 CUJ-3 改名后重试」。
- **bak 文件累积**：每次合并都产生一个 bak 文件，目录会持续增长。MVP 不做自动清理（写权限自己保管）；用户可手动 `rm` 旧 bak。
- **成功页用户没点「继续录入」就关页面**：草稿前端态丢失，但 catalog.yaml 已成功更新，DB 也已同步 — 后果是无（不需要恢复任何东西）。
- **失败页用户没点「返回上一步」就关页面**：草稿前端态丢失，catalog.yaml 已从 bak 恢复 — 用户需从 CUJ-1 重做。这是 MVP 简化（不持久化草稿）的代价，提前在引言段已声明。
- **「查看后端日志」按钮**：MVP 简化实现 — `GET /api/intake/recent-logs?lines=100` 返回最近 100 行后端 stdout，前端在 Modal 内用 `<textarea readonly>` 等宽字体展示。

### Acceptance Criteria

- CUJ-4 点击「下一步」后路由保持在 `/intake`，主区切换为合并预览页，浏览器 tab 标题为「产品录入 · 合并到 catalog」，步骤指示器移到 ⑤。
- 「合并摘要」卡片显示 3 行：① 「N 个新组件」+ 名称列表 ② 「M 张新打印盘」+ 总耗时合计 ③ 「K 个新产品变体」+ 变体名列表。
- 摘要下方有灰底说明条「合并前会自动备份到 `catalog.yaml.bak.<时间戳>`，合并成功后会自动触发『重新加载目录』 — 写入失败时会自动回滚到备份」。
- 「YAML 预览」卡片显示暗黑代码块（`background: #1e1e1e`、`max-height: 520px` + 内部滚动），含 syntax highlighting：键蓝 / 字符串橙 / 数字绿 / 注释绿斜体。
- 预览首行是注释 `# --- <产品基名> 系列，由产品录入工具于 YYYY-MM-DD HH:MM:SS 追加 ---`。
- 预览包含三段：`组件:`（含 `名称` / `描述` / `可选颜色`）、`打印盘:`（含 `盘号` / `组件` / `数量` / `耗时分钟`）、`产品:`（每个变体一条，含 `名称` / `描述` / `BOM`）。键全部为中文（与 `data/catalog.yaml.example` 一致）。
- 「确认合并并重新加载 →」按钮带绿勾 svg 图标；点击后向 `POST /api/intake/merge` 发出一次请求，按钮在请求期间显示 loading 转圈且不可重复触发。
- 合并端点按以下顺序执行：① 撞名兜底校验 → ② 备份 `data/catalog.yaml` 到 `data/catalog.yaml.bak.<时间戳>` → ③ append 写入 + YAML 合法性校验 → ④ 内部调用 `load_catalog(db)` → ⑤ 任一步失败从 bak 恢复 `data/catalog.yaml`。
- 合并成功后主区切换为成功页：浏览器 tab 标题「产品录入 · 完成」，大绿色 `✓` 图标 + 标题「合并成功」+ 描述显示追加的组件/盘/变体数；下方等宽字体显示备份文件名 `data/catalog.yaml.bak.<时间戳>` 与耗时分项 `写入 X ms · 重新加载 Y ms`。
- 成功页底部按钮：「继续录入下一个产品」（secondary，点击回到 CUJ-1 空态、清空所有前端态） / 「前往产品目录查看 →」（primary，路由切换到 `/products`，可见 prd-000 CUJ-1 列表中已包含新合并的产品）。
- 合并失败时主区切换为失败页：浏览器 tab 标题「产品录入 · 合并失败」，大红色 `!` 图标 + 标题「合并失败 — 已自动回滚」+ 描述按 `error_kind` 变化 + 等宽字体显示错误详情块（错误类型 / 错误信息 / 已回滚至 / 建议 共 4 行）。
- 失败页底部按钮：「查看后端日志」（secondary，点击弹出 `Modal` 在 `<textarea readonly>` 内显示最近 100 行后端 stdout） / 「返回上一步调整」（primary，退回 CUJ-4 保留所有变体与颜色填写）。
- 合并失败但已发生备份的情况下，`data/catalog.yaml` 文件内容应与合并前完全一致（通过备份恢复），bak 文件保留不删。
- `error_kind: conflict` 时备份不发生（撞名校验在备份之前），`data/catalog.yaml` 文件未被触碰。
- 合并成功后 `/products` 页面（prd-000 CUJ-1）能立即看到新合并的产品变体（无需用户手动点「重新加载目录」 — 合并端点已内部调用 `load_catalog(db)`）。
